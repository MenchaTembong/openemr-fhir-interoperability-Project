4548‑4
Hemoglobin A1c
The LOINC code I configured, ordered, resulted and retrieved.

A laboratory can call this test HbA1c, Glycated Hemoglobin or A1C. A receiving system matching on the name gets it wrong. Matching on 4548-4 cannot.

I spent the Spring/Summer 2026 term on the interoperability team of a student EMR project, making that exchange work in practice: securing a FHIR R4 API on OpenEMR, loading the terminology behind it, and testing a lab order from the moment a physician places it to the moment the result comes back out as a structured resource.

From the bench to the interface

I worked in a hospital laboratory in Yaoundé before I came to health informatics. I have run the tests this project codes for, calibrated the analysers, kept the quality control, and handed results to clinicians who had to act on them that afternoon.

That is why the laboratory side of interoperability is where I am most useful. When a reference range is stored as free text, or a result arrives under a local code wearing a LOINC label, I know what it costs at the far end: a repeated draw, a delayed diagnosis, a clinician deciding on a number that does not mean what the chart says it means.

My responsibility used to end once an accurate result existed. This project showed me how far that result still has to travel, and how much of the journey is settled by configuration choices made long before anyone draws a sample.

What I built and tested

On a shared OpenEMR 7.0.2 instance running on AWS.

Secured the FHIR R4 API

Enabled the FHIR and REST connectors, registered an OAuth2 client, and scoped it to read-only access on Patient, Observation and Encounter.

Proved live data exchange

Authenticated in Postman and retrieved Patient, Observation, Encounter and DiagnosticReport resources from the running instance.

Loaded clinical terminology

Imported LOINC and ICD-10 into OpenEMR. LOINC is supported as code type 110 but ships empty, so the codes have to be brought in deliberately.

Made a test orderable

Configured Hemoglobin A1c against LOINC 4548-4 with units and a reference range, so a physician could order it and a result could be flagged against the range.

Mapped the data elements

Set OpenEMR's internal fields against FHIR R4, HL7 v2 and C-CDA, then wrote the future-state recommendation that followed from it.

Tested it as the lab role

Laboratory and interoperability tester in a scripted 47-step end-to-end test, responsible for verifying the coding, processing the order and entering the result.

What the data showed

A lab report flags the values that fall outside the expected range. These are the ones I found in ours. Each is reproducible from the sample payloads in the repository.

LOINC codes carried a redundant prefix

BREAKS MATCHING

The system URI already identifies the code system, so repeating it inside the value is wrong. A consumer searching for 2093-3 never finds LOINC:2093-3. It reads correctly to a human and is invisible to a machine, which is the worst of both.

"system": "http://loinc.org",
"code":   "LOINC:2093-3"   → should be "2093-3"

Local codes presented as LOINC

MISLEADING

Some results declared the LOINC system URI while carrying values that are not LOINC codes. Hemoglobin is 718-7. A receiving system has no way to know the claim is false.

"system":  "http://loinc.org",
"code":    "1001",
"display": "Hemoglobin Result"

Environments drifted apart

SCOPE RISK

The hosted instance and a newer local build advertised different FHIR capabilities. Specimen and ServiceRequest existed locally and not on the shared server, so a workflow proven on a laptop could not be promised on the environment we actually presented from.

Reference ranges arrive as free text

DESIGN LIMIT

FHIR models a range as structured low and high quantities. OpenEMR stores the string < 5.7. The abnormal flag works because OpenEMR evaluates it internally; anything downstream has to parse prose first.
